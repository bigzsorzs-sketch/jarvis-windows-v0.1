# Jarvis v0.3.24

GitHub-based Self-Repair release candidate for the Windows desktop application.

- Allow the local owner to connect the pinned Jarvis repository using a fine-grained GitHub token stored with Electron safeStorage; the credential is not passed to the AI or renderer status.
- Prepare a minimal, exact-hash repair plan, then validate the approved source in isolated staging after a clean dependency installation, complete source tests, lint, typecheck, policy checks, and renderer build.
- Restore the staging workspace before sending only the validated changes to a dedicated GitHub repair branch and Pull Request; do not activate an unverified local runtime.
- Protect trust-core files, release tooling, CI workflows, version metadata and existing tests from AI-authored patches.
- Verify that a reused repair branch has the original one-commit parent and exactly the approved file diff, rejecting unrelated or extra changes.
- Verify independent CodeQL and Windows CI jobs at the exact PR head SHA, and refuse merge if the original main commit has changed.
- Keep PR abandon, merge and release as separate owner-approved operations; correctly handle GitHub's prospective merge SHA on unmerged PRs.
- Bind release dispatch to the exact merged main SHA and version, and require independently successful main CI before requesting publication.
- Require the published release manifest to agree with the installer version, SHA-256 checksum, main commit and release target before handing the installer to Windows; preserve Authenticode verification where available.
- Show connection status, repair PR, CI state and subsequent update actions inside the Self-Repair System Center.

## Verification

This release candidate must pass the complete branch and main CI pipeline, including CodeQL, JavaScript source tests, lint, typecheck, production dependency audit, Jarvis policy verification, renderer build, staged Self-Repair toolchain tests, admin-helper test, packaged startup smoke test, installer checksum and manifest validation.

The connected GitHub-token flow, actual network failures, live Windows repair round-trip, large installer download, and backup/restore after installation require hands-on testing on Windows before the module can be considered fully acceptance-tested. An unsigned installer is not proof of trusted publisher identity; unsigned publication requires separate owner approval.
