# Jarvis v0.2.7 — Controlled Self-Development

## Goal
Turn Upgrade Center into a real approval-gated development workflow. Jarvis may diagnose a bug or feature request, research/compare candidate solutions, and present a concrete implementation proposal. It must never modify source or installed application code before explicit owner approval.

## Required transaction
1. Capture bug report or feature request.
2. Collect diagnostics and relevant project context.
3. Research candidate approaches using configured AI/research providers.
4. Present evidence, alternatives, chosen approach, affected files, expected behavior, risks and validation plan.
5. Require explicit owner approval bound to the exact proposal hash.
6. Create a recoverable backup/snapshot before any write.
7. Apply only the approved patch inside an allowlisted project workspace.
8. Never modify the policy engine, signed core rules, owner authorization, updater trust controls, secrets, or rollback controls through self-development.
9. Run syntax checks, tests, lint, typecheck, security verification and build as applicable.
10. If validation fails, rollback automatically and report the failure.
11. If validation passes, show the exact diff and results. Publishing/releasing remains a separate explicit owner action.

## State machine
DRAFT -> ANALYZING -> PROPOSED -> APPROVED -> SNAPSHOTTED -> APPLYING -> VALIDATING -> VERIFIED
Failure after SNAPSHOTTED -> ROLLING_BACK -> ROLLED_BACK
Owner rejection -> REJECTED

## Approval integrity
Approval is valid only for one immutable proposal hash containing:
- requested goal
- exact patch/diff
- affected file list
- validation commands
- risk classification

Any change to the patch invalidates approval and requires a new approval.

## Workspace rules
- Writes allowed only in a separately configured development workspace, never the packaged ASAR/install directory.
- Path traversal and symlink escape must be rejected.
- Protected paths include electron/security/**, security/**, updater trust/verification logic, owner PIN/authorization code, and rollback implementation.
- No arbitrary shell command supplied by an AI response may execute.
- Validation commands come from a fixed application allowlist.

## UI
Upgrade Center must clearly display:
- problem/goal
- candidate solutions and rationale
- recommended implementation
- exact affected files and diff
- risk level
- backup status
- test/build plan
- APPROVE / REJECT controls
- execution log
- rollback status
- final verified status

## v0.2.7 acceptance criteria
- No source write occurs before exact-plan owner approval.
- Changed proposal invalidates prior approval.
- Protected paths cannot be patched.
- Failed validation restores the snapshot.
- Successful validation records an audit trail and exact diff.
- Existing v0.2.6 updater/self-repair tests remain green.
- New regression tests cover approval bypass, path traversal, protected paths, patch mutation and rollback.
